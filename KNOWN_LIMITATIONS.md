# Known limitations

## Line endings in files the model did not edit (fix in progress)

When a run edits files in place, text files in the edit scope that the model did not change can still be rewritten: Windows (CRLF) line endings, old Mac (CR-only) line endings, mixed line endings and a leading byte-order mark can come back changed. The same changes appear in exported patches, so applying a patch with `git am` carries them too. Files with plain LF line endings and no byte-order mark are not affected.

Until the fix ships: after a run, review `git diff` (or the exported patch) before committing, and restore any file you did not expect to change with `git checkout -- <file>`. Runs that do not edit in place leave your repository untouched, but their patches have the same issue.

## Linux checks that run Go or Node

Linux: checks that run Go or Node programs fail under StateFrame's check memory limit. The limit caps virtual address space (`RLIMIT_AS`), and those runtimes reserve far more address space than they use, so they exit at startup. macOS ignores that limit and is not affected. This has been true since at least 0.3.30 and is fixed in the next release.

## Environment seed storage

The `STATEFRAME_ENV_SEED_MAX_GB` cap is soft: the newest seed and seeds in use can keep the store above it. On Linux, a seed whose files are still hard-linked into a run environment cannot be evicted until that run is removed with `stateframe gc`.

## Hosted OpenAI-compatible endpoints

Without either a llama.cpp-shaped `GET /props` response, a populated, typed `GET /slots` response, or the explicit `STATEFRAME_PROVIDER=llama.cpp` override, endpoints use the strict OpenAI Chat Completions request schema. StateFrame removes llama.cpp-only fields and drops configured `top_k` and `min_p`; `n_probs` is mapped to `logprobs` and `top_logprobs`. `reasoning_effort` is sent only when `REACT_REASONING_EFFORT` is explicitly set to a documented OpenAI value (`none`, `minimal`, `low`, `medium`, `high`, `xhigh`, or `max`) and is the operator's confirmation that the selected endpoint accepts that field. A profile that globally disables reasoning needs `REACT_REASONING_EFFORT=none`; otherwise the request is refused.

The llama.cpp `/tokenize` endpoint is not used without dialect proof. Strict hosted generation endpoints use the request meter's calibrated byte estimate unless `LLAMA_CPP_TOKENIZE_URL` points to a separate tokenizer origin that proves llama.cpp; that estimate can be less exact than tokenization by the model server.

Hosted endpoints cannot use prompt-cache reuse, KV chunk reuse, self-plan prefill, true prompt continuation, routed static slots, history-compaction cache/slot, or public-review `cache_prompt` unless `/props` or a typed `/slots` response proves the selected origin is llama.cpp, or the operator explicitly sets `STATEFRAME_PROVIDER=llama.cpp`. The shipped profile's automatic prompt-cache pin degrades when `/slots` is unproven and does not block an otherwise valid request; StateFrame reports the reason in the CLI summary and journal. Selecting an actual cache request or slot still requires proof. Study capacity preflight is restricted to a loopback llama.cpp endpoint; template-conformance `/apply-template` calls require llama.cpp dialect proof. Any slot ID or save/restore/erase operation still needs a successful `/slots` proof and a reported slot ID. History compaction with `cache_prompt=true` also needs an explicitly selected slot reported by `/slots`. Unsupported selections fail with a typed capability error rather than silently changing behavior. The override trusts the operator's dialect choice; it does not prove slot support. No slot ID is invented.

## Request-compatible digest residual

`_revision12`, `dependency_revision`, the source-closure revision, the coordinated-change tree revision, and `kernel_state_owner_inventory._source_revision_vector` keep the 0.3.18 encoding for readable NUL-free regular files so that request bytes stay identical. That encoding puts no terminator after a file's content, so two different lists of files can produce the same revision when one file's content ends with the start of the next path in the other list (`a`="bc", `d`="e" equals `a`="b", `cd`="e"). Their comparing cache keys and closure freshness checks now include the ordered path list. A fully typed encoding for these sites is planned for a release that is allowed to change request bytes; no version is set. The digest class guard's allowlist is empty.

## Supported environment

This preview is supported on macOS on Apple silicon and on Linux x86_64 (tested on Ubuntu 22.04.5, kernel 6.8, Python 3.11: install, the three demos, the bubblewrap sandbox with no network and no writes outside the run, and `kill -9` then resume all pass). Long runs (200-300 requests) and the speed and memory numbers were measured on macOS only; Linux is tested end to end on short runs. Checkpoints were measured on macOS; on Linux, resume is verified through full replay. Linux arm64 preview runs are untested. Ubuntu 24.04 and later restrict unprivileged user namespaces, which bubblewrap needs; that release is untested, and if the sandbox cannot start there the usual setting is `sudo sysctl kernel.apparmor_restrict_unprivileged_userns=0` (or an AppArmor profile that allows `bwrap`). Docker is not supported. Use Python 3.11 or newer with venv and ensurepip (Python 3.14.1 is not supported: the pinned networkx 3.6.1 excludes that one release; other 3.14.x releases work). The installer downloads pinned, hash-checked dependencies from PyPI; `./install.sh --offline` uses the bundled wheelhouse instead, without schema validation or the syntax-aware repo map.

The new command containment path was exercised in a Linux aarch64 container. Its x86_64 path has not been verified for this tool release. That is separate from the earlier Linux x86_64 preview checks above.

## Request and model capacity

Request body compression is off by default because stock llama-server does not accept gzip request bodies. Enable `STATEFRAME_HTTP_GZIP=on` or `STATEFRAME_PLAIN_GZIP=on` only in a custom profile for a relay that inflates them. In the default run mode, a compressed request refused with HTTP 415 is resent once without compression within the same deadline. If the run deadline stops a request while that uncompressed resend is in flight, the error is recorded but the two attempts are not listed separately.

A request body that stops making send progress is aborted after `STATEFRAME_SEND_STALL_S` (90 seconds by default; 10 to 600 seconds). It can retry on a new connection within the existing transport attempt and run deadlines. A provider that received part of the body may still have work to discard; StateFrame cannot prove what an intermediary did with those partial bytes. Healthy probes extend queue time only after the full body is sent.

A profile that sets `STATEFRAME_SEND_STALL_S` or `STATEFRAME_QUEUE_WAIT_MAX_S` is refused by earlier StateFrame versions with "unconsumed STATEFRAME settings". Keep a separate profile for older installs.

The engine has a **33,344-token prompt budget** and requires a model server context slot that supports **65,536 tokens**. The slot is server capacity, not a recommendation for cache RAM. Set cache RAM sized to your machine. These are the sizes we built and measured with: a single 48 GB GPU (RTX A6000 class) running Qwen3.6-35B-A3B, a mixture-of-experts model (35B total, about 3B active per token), 4-bit UD-Q4_K_XL, under llama.cpp, with one server sharing a 262,144-token cache across 4 slots (`-np 4 -c 262144 --kv-unified`), so 65,536 tokens per run. A stock 24 GB card was not tested. They are the defaults; both can be changed (see Context size in docs/guide/running.md). Only the default 65,536-token slot is measured on long runs; other sizes (32,768 and 131,072 included) are tested on short scripted runs only.

Large tasks or repositories can require more state and source context than fits. In that case, the engine may stop before completing the task.

- Very long tasks (roughly 25 or more model turns) and larger multi-file changes (around 10 files or more) can stop with a refusal when the task state no longer fits the prompt budget. Nothing is lost: the partial result is saved.
- On repositories with more than about 12 source files, runs now start, but a longer run can still stop mid-run with `FrameRequestAllocationError` (`closure_units_undelivered` or `source_delivery_partial`) after the agent has read many files and the request budget has to drop earlier read pages. In the live measurement on a 22-file, 1,277-line repository, runs that 0.2.8 refused before the first request sent between 6 and 25 requests in four runs before stopping. The partial result is saved. 0.3.5 fixes one cause, a stop on `source_delivery_partial` after the agent re-read a file an earlier request had deferred; a recorded run that stopped that way now finishes. Other causes of a mid-run stop on larger repositories may remain.
- Shell, job and custom-command reply delivery shrinks against the measured whole request when a populated frame nears the prompt limit. The full taped observation remains on disk, subject to the command collector's output cap. If the authoritative minimum still cannot fit, the request is refused.
- Project instructions (`--instructions`) are off by default. In a live comparison on Qwen3.6-35B-A3B, the three bundled examples passed 9 of 9 runs both with and without a realistic `AGENTS.md`, using 27 and 28 model requests in total, so no gain was measured; these examples are short enough that both arms are at the ceiling. On two harder multi-file tasks scored with hidden tests, a generic `AGENTS.md` (layout, commands, style) scored the same as no instructions. An `AGENTS.md` that also asked the agent to re-read the request and check every requirement it names showed no reliable gain: on the first task, 2 of its 5 runs passed 8 of 9 hidden tests and 3 passed 2 of 9, while all 5 runs without instructions passed 2 of 9; the second task passed in nearly every run of every arm. The engine-side `STATEFRAME_REQUIREMENT_RECHECK` switch does that check without project instructions (see [Running](docs/guide/running.md#closing-check-requirement-recheck)). At most 6,144 bytes of the file are shown, and the text is untrusted repository content, not a security boundary.
- Selected skill descriptions are visible in the typed frame. Skill bodies are delivered only after `skill_load`, with at most two resident bodies. Other files in a skill directory are not shown to the model. Bodies may be omitted to fit the prompt budget, then loaded again. Skill text is user content, not a security boundary.

## Agent tools

- Supervisor diagnostics for startup probes and import smoke are best-effort: the exit code is included only when the retained process reports one, and the log tail is capped at 8 KiB. A missing or unreadable supervisor log is reported as absent.
- Shell, delete, move, read-only Git, opt-in web fetch, background jobs, explicitly configured command tools and opt-in MCP stdio tool servers are available. MCP HTTP transport, resources, prompts, sampling and persistent sessions are not. On macOS, stdio servers must be single-process programs; wrappers that spawn children need a direct final-program argv. See [Agent tools](docs/guide/tools.md).
- MCP tools and configured command tools are callable while the agent explores, but late phases (after the first edit, while verifying, and when closing out) narrow the current-step tool menu. With the stable tool list on by default, definitions seen earlier can remain visible even when they are no longer callable; a call outside the current menu is refused with `not offered for the current state`. A needed lookup may be unavailable after editing starts, so ask for it early in the task.
- For shell commands and background jobs on macOS, a process deliberately double-forked and orphaned between supervisor sweeps can outlive a run. Its sandbox profile continues to restrict filesystem and network access. A detached descendant that is still seen is stopped by a signal the kernel delivers only if the process's PID generation still matches; if macOS cannot report that generation, cleanup reports the process as a survivor instead of signalling it. If the kernel's generation-checked signal is unavailable, StateFrame falls back to re-checking the process identity immediately before a numeric-PID signal; a PID reused in that instant could be signalled. Linux uses pidfds for descendant and orphan-guard signals when available; when `pidfd_open` fails, the test-only orphan guard rechecks process start identity immediately before a numeric-PID signal, which retains a narrow PID-reuse race. Aggregate resident memory is polled rather than enforced as a hard cap, so usage can overshoot between samples.
- After a command's leader exits and is reaped, cleanup still tracks processes in its process group or session if they started no later than the reap; a reused leader PID's new group starts later and is not adopted. Start times have clock-tick resolution on Linux (/proc, usually 10 ms) and microsecond resolution on macOS, so a reused leader whose new group starts within the same tick as the reap would be adopted and could be signalled during cleanup.
- If an outer-check helper dies before acknowledging process cleanup, the parent cannot prove it stopped a check descendant that escaped the helper's process group. It reports `outer check containment unverified` rather than a clean check result; an escaped descendant may remain until it exits or is stopped separately. The helper acknowledges process cleanup before removing its temporary repository copy, so slow file removal does not turn a completed process cleanup into this uncertainty.
- Linux checks and commands set a finite task limit from real-UID threads visible inside their PID namespace plus headroom. Checks and commands also use a per-command cgroup `pids.max` when a delegated writable v2 subtree is available, with supervisor descendant counting for commands. Hidden tasks and tasks created during the `/proc` scan can still make the UID-wide limit refuse safe work or allow an overshoot when no cgroup is available; inherited lower hard limits can also prevent startup.
- Linux has one network placement per execution session. A full-network session cannot later use the same shared loopback namespace; a narrower command gets its own loopback namespace and cannot reach a service in the full-network namespace.
- Background jobs are stopped at completion and are not relaunched on resume. A running job from the stopped attempt appears as `lost on restart` when the run continues.
- External operations, including full-network shell calls and custom tools marked `external`, are never repeated automatically on resume. `--replay-external` repeats them knowingly; the command may repeat an outside effect. An incomplete tool operation refuses resume because its outside effect cannot be inferred from the run record.
- Network package installs need `--shell-network full`. The default loopback mode cannot reach package indexes. A run-local install does not update the project's dependency declaration. If a selected virtual environment cannot be safely cloned or remapped, the run environment is disabled with a message.
- Web fetch is off by default, accepts public HTTP(S) text only and blocks private addresses, including redirects to them. Its untrusted-content label is not a prompt-injection security boundary.
- Shell output is neither revision-bound source-read evidence nor engine check evidence. Use `read` and `run_tests` respectively. A command that exits zero or runs pytest itself does not complete a task.
- A source-read sub-task with no turns left whose read fails ends the run `CONTINUATION_BLOCKED` and names the read instead of retrying.
- Custom command definitions require a finite positive timeout no greater than 600 seconds; larger values fail at load.
- Executable-bit changes are refused and restored, including creation of executable files. Shell deletion of an executable is refused; `file_delete` supports intentional removal, while `file_move` refuses executable sources. The sealed candidate does not carry executable-mode changes.
- Workspace reconciliation stops without promoting command effects when any regular file exceeds 16 MiB, aggregate regular-file bytes exceed 256 MiB, or the tree exceeds 20,000 entries. These bounds also apply before execution when the snapshot is captured.
- The shipped product profile uses the composed loop. The plain loop accepts foreground shell but refuses background jobs and Git, web or custom tool settings before execution. Lean mode is not supported by the product profile.

## Lifecycle hooks

Hooks always use the execution sandbox. There is no host-execution option or unsandboxed fallback; a sandbox startup failure is a hook error. Windows is unsupported. Linux desktop notifications cannot reach the user's D-Bus session from the sandbox; use an explicitly configured webhook instead. On Linux, network mode `loopback` gives a hook its own private loopback, so a service listening on the host's loopback needs `full`. The macOS notification and webhook samples are examples and are not exercised by the automated end-to-end tests.

If a process is killed while a hook has a durable intent but no completion record, StateFrame cannot know whether an outside effect occurred and refuses to resume that run. Completed hook decisions are served from the run tape. A hook script is pinned, but a hook that deliberately runs project code from the mutable working copy can be influenced by the agent's edits to that code. The `[USER HOOKS]` label describes the text's source; it does not make that text a prompt-injection boundary. See [Lifecycle hooks](docs/guide/hooks.md) for the write, network and size limits.

## Powerups

Offer and auto rules are evaluated once at run start; a file the agent creates later does not switch a powerup on. When a command or MCP powerup is active, user MCP servers are started once more in a temporary repository snapshot to measure the tool schema allowance, because the engine's own discovery depends on the run's workspace. Powerup tools are capped at six per run. A malformed `powerups.json` state file turns every powerup off for that run, with a notice naming the file, rather than falling back to manifest defaults. Promoted powerups that declare a `mutation` executor are skipped until an executor is registered. See [Powerups](docs/guide/powerups.md).

- Under `--shell unrestricted --shell-sandbox off`, powerup command tools run unsandboxed with full host access as the user running StateFrame, like every other shell tool; MCP servers and hooks stay sandboxed.
- `--powerup NAME=on` runs an installed powerup that was never enabled, because naming it on the command line is treated as the operator's choice; a changed tree is still refused.
- Promotion provenance is read from the run directory, so a user who can write that directory can forge it. Promoted units still install off and need `enable`.
- A local process running as the same user can swap a powerup between its final digest check and use, or edit the run spec that resume compares against. Private directories limit this to the user's own processes.
- A string setting is passed as one whole argument but is not otherwise restricted, so a value can be read as an option by the program, and `test-gate`'s `check_command` chooses the program it runs. Settings come only from the user, the command line or a trusted project.

## Checks

Ordinary non-verbose `go test` output reports package success without a positive test count, so it receives the weaker `verified by check command` label. Use `go test -v` to include named passing tests for test verification.

Go and Rust command paths are implemented but their toolchains are not exercised on this project's automated gates. A repository with no tests can still finish from a passing declared build or type check, an agent-written check with a failing parent and passing candidate, or an unverified result when no check exists. Structured wrong-test evidence is advertised on an explicit `--protect-tests task|off` selection, or `all` for a generic runner; omitting the new flags preserves the 0.2.6 request schema.

The `--protect-tests task|all` guard refuses files that would run at test collection, closing the reported route. StateFrame does not yet check whether a shipped artifact was produced only as a side effect of running an unshipped test-tree file during the run; product code executed under the test harness can still create files the result depends on.

When tests exist, the default check uses pytest test files (`--check` names them), and its engine checks support per-test selectors. A non-pytest `--test-cmd` uses one whole-command result by exit code, with no per-test selector or collection evidence. A command that cannot start, exits 126 or 127, or times out cannot pass. Without tests or an explicit command, StateFrame tries a declared build or type check, then an agent-written check. With no check, the result is `unverified: review the diff`; it is not a test pass. Checks run under the existing sandbox. A generic check needs a usable Python interpreter for StateFrame itself, but that interpreter does not need pytest. The check can inspect output files, not only code (see "Tasks whose output is files" in the README). Test weakening detection for JavaScript, TypeScript, Go, Rust and shell is heuristic and can miss changes in meaning.

In a repository with more than 200 source files, only a chosen set of files is editable: the ones named with `--target` and `--edit`, or else up to 12 files chosen from the task text and the chosen checks' imports. The rest of the repository stays available as read-only context. By default, edit and file-operation tools refuse an existing product file outside that set before changing it. The reply names the path and suggests `--edit PATH` or `--edit-scope widen`. If the automatic choice misses the file the fix needs, rerun with `--edit`, or opt in with `--edit-scope widen` to let edit and file-operation tools admit up to 24 existing product files, including files outside the starting directories. Tests, named checks, hook inputs, links and special files are refused. New-file roots do not grow. A shell command cannot initiate widening: its first write to an existing file outside scope is restored and reported as refused. If a sealed candidate still contains such a change, the host warns and does not report a successful result. Widening turns off checkpoint restore for that run (resume replays instead).

## Optional analysis

Namespace evidence for database-backed cases is limited to source observations. StateFrame does not probe a local database port; when runtime acceptance cannot be observed, the evidence and run summary report `runtime_namespace_acceptance_not_observed` instead of claiming the check passed.

- **Syntax-aware repo map: on by default** for 12 languages (Python, JavaScript, TypeScript, TSX, Go, Rust, Java, Ruby, PHP, C, C++, C#), each from its own MIT grammar package. For HTML, CSS, JSON, TOML and YAML files the engine reads structure (ids and headings, selectors, keys, tables) from five more grammar packages. Other languages, including Vue, use the built-in text-scan repo map. `./install.sh --no-repomap` skips it.
- **Named working sets are not available to the model in this release.** The engine keeps its own set of files it is working on, but the tool that lets the model name and manage working sets is not offered in its requests yet.
- **Offline install** (`--offline`): schema validation and the syntax-aware repo map are OFF; the engine skips schema validation and uses the text-scan repo map.

## Files dropping out of long runs

To stay inside the prompt budget, the engine evicts file contents the model read earlier. Usually the task state says which file was evicted. On long runs that read many files, some evictions carry no notice. Measured on one long task: 0 of 15 checks unannounced at request 11, 30% at request 30, 45% at request 61. The model can read the file again. `STATEFRAME_EVICTFIX=on` (opt-in, off by default) keeps more recent reads in the frame, but in this release it makes host time per turn grow on long runs, and we have not measured an edit gain from it.

## Experimental switches

`STATEFRAME_MICROGRAPH=on` is experimental and off by default. With it off, requests are byte-identical to a build without it. We have not measured whether turning it on helps, so we make no quality claims for it.

## Models

This release has an early five-run result on the previously stalled multi-file refactor: Qwen3.6-35B-A3B submitted with all 14 tests passing in all five runs. On 0.2.1, Qwen3.6-35B-A3B solved the HTTP transport task (graded as a correct candidate), while the same refactor ended in a no-progress stop. DeepSeek V4 Flash solved the refactor on that build in 2 of 2 runs, with all 14 tests passing. These small samples are smoke tests, not success rates. On an earlier release, Flash also solved the HTTP transport task and solved a harder multi-step task in 1 of 2 runs (hidden tests); the other run exhausted its request budget mid-fix. Repeated reads can still occur on a larger single-file task. Other models are untested.

## Per-step models

- A routed run's in-flight request (the one that had no reply when the run stopped) is checked against its rebuilt copy on the first resume. On later resumes it is checked only if the previous resume recorded that its own check passed. Otherwise, for example when a resumed run stops again before its check, StateFrame resumes by full replay without an in-flight check, prints a line saying so and records it in the run.
- Routed runs with checkpoints enabled: resume replays; checkpoint restore of routed runs is not supported. Checkpoints are still written if `STATEFRAME_CHECKPOINT=save` is set, but a routed resume never uses them.
- If only a route record was written before a stop, the original send had not started. Resume checks the route, then sends the rebuilt request live. Replay also masks standalone 32-character hex values, test durations and object addresses; a meaningful change with one of those shapes can compare equal.
- Roles are assigned mechanically. The engine cannot tell reading from editing before the reply, because the tools it offers do not depend on what the step is for. So an edit step first goes to the model of the role it was assigned, usually `read` (or `plan` on the first request and after a failed test run); if that reply writes files it is thrown away unrun and the step is asked again of the `edit` model. Each edit step costs one extra request on that first model.
- Shell commands are not escalated. A `shell` call counts as a reading step and runs on whichever role's model asked for it, even when the command writes files, so a `read` model can change the working copy through `shell`. The sandbox and effect checks still apply and record every change. Use `--shell read-only` to prevent this.
- Switching models between requests resets the server's prompt cache for that request, so a routed run reuses less cache than a single-model run.
- The token allowance for chat-template overhead is calibrated on Qwen3.6-35B-A3B. Each role's tokens are counted on its own server, but a model with a much larger template can come close to its slot on the largest frames.
- Every role's server slot must be at least the run's context size (65,536 tokens by default). A small model served with a smaller slot is refused at start when its server reports the slot size; a server that reports none is not checked.
- Routed roles speak the OpenAI-compatible chat API. There is no provider-specific adapter yet.
- Routing makes a run cheaper only when the `read` model is good at the tool protocol. In our first live check (the discount_bug example, reading on MiniCPM5-1B, everything else on Qwen3.6-35B-A3B), both runs passed the tests. The routed run needed 38 requests against 3, because most of the small model's replies made no tool call or ran to their token limit, and it took over 20 times as long. Try a read model on a short task first, and cap `read.max_tokens`.
- Cost figures are estimates from the rates you set, using the token counts each server reports. A server that reports no usage leaves its cost unknown.

## Multi-file source and repeated reads

With `STATEFRAME_CODE_BOOKMARKS` on by default, the frame offers current editable product source before repeated-read and navigation bookkeeping. Each editable product path has a coverage line showing which source ranges are in view and whether the source changed since its last read when that comparison is available. Files of at most 60 lines and 2 KiB can be shown whole when the request budget allows. Very large repositories still get selected windows, not every whole file. Bookmarks use a current failing check to keep its test code and related product source in view, but need a usable source location. Setup and collection failures, and failures without a `file:line`, do not activate them. Set `STATEFRAME_CODE_BOOKMARKS=off` to restore 0.2.1 behavior byte for byte.

Measured so far on one multi-file task that had stopped on every previously observed build: all five current live runs completed and were submitted, with all 14 tests passing (three on an earlier build of this release, two on the release code). This is an early result from five runs, not a general success rate. In an offline rebuild of one recorded request, the frame showed 11 of 11 product files whole, up from 1 of 11; complete request size fell from 85,664 to 77,017 bytes, below the 82,026-byte ceiling.

A completed batch made up entirely of unchanged reads costs one no-progress watch unit, rather than one per file. Mixed or unproved batches keep per-action accounting. If the model continues to repeat unchanged reads, the run still ends with `STALLED` and preserves its partial changes for inspection.

The optional `STATEFRAME_READ_LOCKOUT=on` restriction is off by default. When enabled, it can hide source-reading routes for up to two requests after unchanged reads, while a current failing check, editable bookmarked source, and an edit and check route are available. If the no-progress watch is one step from its limit, it can stop the run before the restriction takes effect.

## Memory on long runs

This release moves run history out of memory (see "Disk use for run history"). Measured on a release-candidate build in short runs: the engine's memory footprint held at about 1.7 GB from request 10 to 60 (1,723 to 1,782 MB), growing about 0.8 to 1.1 MB per request between requests 20 and 40. The 1.7 GB is a fixed base, mostly repository analysis, and grows with repository size. Runs past about 60 requests on this build are still being measured. Measured on the previous engine (before this change), on one long task: memory grew about 12 to 30 MB per model request, about 11 GB at 240 requests. Measure footprint (Activity Monitor "Memory" or `top -stats mem`), not `ps` rss, which leaves out compressed memory.

## Engine time per turn on long runs

The prompt stays the same size every turn, and on this release's build the engine's own time per turn stays about flat on runs up to about 60 requests. Older engines grew on long runs. Measured on an older engine, in one live long run: median engine time per request went from 8.0 s early in the run to 19.3 s by request 200. On a 55-turn replay of the build this release is cut from (same engine code, comments cleaned), median engine time per turn went from 15.2 s to 16.9 s, and on a 60-request live run the engine's own time between responses did not trend up (about -4 ms per request). Runs past about 60 turns on this build are still being measured.

## Disk use for run history

The engine keeps each run's request history in spool files on disk instead of in memory. Once the run journal is open they sit in the run directory (default `~/.stateframe/runs/<repo>-<time>`, or the folder you pass with `--run-dir`); before that, briefly, in a private `sf-history-run-*` folder under `/private/tmp` (or `/tmp`). It grows with the run; see Requirements in README.md for free disk. The files are opened and then unlinked, so `ls` and `du` do not show them while the run is open; `df` does. They are released when the run closes. A run that is killed can leave an empty `sf-history-run-*` folder behind, which is safe to delete. Checkpoint copies of the history are kept in `<run-dir>/checkpoints/journal-cache` until finish-time retention or `stateframe gc` removes them. Uninstalling StateFrame does not remove run directories; use `stateframe gc` to review reclaimable storage or delete run directories when you no longer need to inspect them.

This behavior is always on in this release and has no setting.

Measured on a large repository without checkpoints: a run directory uses about 3 MB per request, about 550-750 MB for a 209-request run. The largest parts are the run's journal and history (about 200 MB, needed by resume and replay), saved candidate snapshots (about 130 MB), copies of the repository (about 30-75 MB each) and the recorded requests (about 23 MB). Checkpoints come on top while the run is live (see "Resuming a stopped run"; on by default).

Finished runs remove checkpoints and the run environment by default, while retaining the manifest needed to rehydrate that environment. A finished run directory also stores its measurement journal as `events.jsonl.xz`, journal blobs in one pack and preflight requests in `requests.pack.xz`, so scripts that read the loose files of older releases need updating; `--keep-run-env` keeps `env/` and `--keep-checkpoints` keeps checkpoints. `stateframe gc` is a dry-run preview by default; use `--apply` to reclaim eligible older-run storage. On ext4, environment seeds use hard links when possible because reflinks are unavailable; offline rehydration needs the required wheels in local caches or a wheelhouse. Once its seed is gone (pruned by `stateframe gc`, or on another machine), `stateframe rehydrate` reinstalls with pip, and a project installed from a local directory that no longer exists is reported as a mismatch instead of restored. Run directories started on an older release cannot be resumed after upgrading, because resume needs the engine release that started the run: `stateframe resume` says "cannot resume: this run was made by engine release <old>, the installed engine is <new>; resume replays the run on the same engine, so it needs the release that started it". Resume them with that release. `stateframe inspect`, request records, measurement journals and `stateframe gc` still work on them. `stateframe rehydrate` refuses them because they have no manifest: "<run> has no env-manifest.json; it still has its environment in env/, so there is nothing to rehydrate" (or, without env/, "<run> has no env-manifest.json, so its environment cannot be rebuilt; runs made before StateFrame recorded one have no manifest"). See [Run storage](docs/guide/storage.md) for formats and commands.

## Identical runs and request bytes

The engine normalizes volatile test and tool output (test-runner durations, memory addresses in tracebacks, run-directory paths) before the model sees it; the raw output stays in the run journal. On the measured 40-request workload, two runs on the same input sent byte-identical requests on 40 of 40 requests, apart from three clock fields. The IDs the engine shows the model (edit receipts, check receipts, request IDs) come from the task, the step and the content, so two runs of the same task that take the same path give them the same values. Tool output the engine does not recognize as volatile can still differ between runs. This is not full determinism. The model's own output is not deterministic, so a live run can take a different path. On purpose, the engine still shows the model some real clock readings: the time in the environment panel, how long a job has run, and when a navigation handle expires. A few rarely used paths still use random ids, the ones that continue an interrupted intention, fork work, or run several attempts side by side, so runs that take those paths can differ in request bytes.

## Prompt cache reuse

Prompt cache reuse is still bounded by the state frame. The tool list is stable by default, which lets the provider reuse the tool schemas, system prompt and task after the first request. The state frame remains one message that changes every turn, so the cache must start again at that message. In the measured comparison, cached share after the first request was 14-22% on the bundled examples. See [Running](docs/guide/running.md#prompt-cache-stable-tool-head).

The final cache layout, on by default since 0.4.0, raised the cached share after the first request to 28% on a long 22-file task and 32% on a smaller one in the measured comparison, from about 23% with it off. That is still well below what plain chat history gets from the same server, and below the 40-45% we are working towards; the next releases target where consecutive requests stop sharing a prefix. On long runs under heavy budget pressure, some requests cannot be fitted in the cache-friendly order and are sent in the plain order instead (a `final_cache_layout_failed_open` event; 2 and 6 requests in two of the three long runs measured). Those requests get no benefit from the layout.

`STATEFRAME_STABLE_WIRE=on` is an experimental opt-in layered on the final cache layout. Experimental; in live testing it can end a run with StableWireError when a delivered source window is re-rendered. A fix is planned; leave it off. It keeps windows that are no longer current in the prompt until an epoch rebase; the status row labels them, but the model can still misread stale lines as current. The source-delivery proof checks current obligations and does not independently prove that model actions ignored retained content. `STATEFRAME_STABLE_WIRE_HEADROOM` defaults to 16000 tokens; values under 6000 are refused because measured compactions every 2-3 requests erase the gain. An offline comparison on recorded runs measured a better score at 16000 than 12000; live runs have not confirmed it yet. Keep it off for ordinary runs.

## Token counting

- When the model endpoint provides a valid `/tokenize` response, StateFrame uses it for exact token counts. `LLAMA_CPP_TOKENIZE_URL` can point to a separate tokenizer. Each count against a remote server adds a network round trip; a local tokenizer can avoid that delay (QUICKSTART.md). llama.cpp is the tested server type; other server types are untested.
- If the selected endpoint cannot provide a valid tokenizer response, StateFrame uses a conservative estimate. A run can stop before its first model request if even the smallest request does not fit.
- When tokenization becomes unavailable mid-run, StateFrame falls back to a calibrated byte estimate with a raise-only density floor for dense content. The estimate was about 39% high on average in measured requests, so runs without exact tokenization fit less content, but very dense content such as long runs of numbers, base64 data, or dense code can be underestimated and push a request past the server's context limit. Keep the tokenizer available for the whole run.
- A recognized HTTP 400 for a context-limit overflow can trigger one smaller request with reduced byte and token limits when time and a retry attempt remain. Other HTTP 400 responses do not trigger this retry. If the retry is rejected or the minimum request cannot fit, the run ends incomplete. An available `/tokenize` endpoint is the most reliable choice for dense files.

## Endpoint locality

Remote endpoints are rejected by default. An explicit override can enable them and warns that source code will leave the machine. A loopback endpoint may also forward elsewhere, so local-only endpoint checks cannot verify the server's upstream route.

## Internal identifiers

Internal identifiers keep development names (profile keys, module filenames, schema IDs).

## Editing files during a run

If files in the working copy change while a request is being prepared (for example, you edit a file mid-run), the engine refuses that request rather than send stale content. Avoid editing the working copy during a run.

## Slow or shared hardware

Each model request normally has a 600-second timeout (`STATEFRAME_PER_REQUEST_TIMEOUT_S`). While no response bytes have arrived, StateFrame probes `/slots` and `/health` at the selected endpoint's origin with the request's key. Any HTTP answer, including 401, 404 or 503, permits a longer queue wait. `STATEFRAME_QUEUE_WAIT_MAX_S` caps the total silent wait at 1800 seconds by default, or the remaining run deadline if shorter; it must be finite and positive and can be set in the environment or a profile. A probe answer does not guarantee the model request is progressing. If probes give no answer for 90 seconds by default (`STATEFRAME_PROVIDER_LIVENESS_S`, which only a profile file can change), the request fails; with no successful probe by the per-request deadline, that deadline still applies. Once response bytes arrive, the per-request limit bounds a stalled response. A timed-out send may be retried, and the server may finish an abandoned attempt anyway, using GPU time. On slow hardware, give the model server the GPU to itself during a run.

## Time and step limits

There is no time limit by default: a run continues until the engine finishes, and you can stop it any time with Ctrl-C. Pass `--timeout <seconds>` to set one. The request, queue-wait, liveness and run deadlines still bound silent or stalled model calls.

There is no step limit by default either. Pass `--max-turns N` to stop after N model turns.

## Resuming a stopped run

- Checkpoints are on by default. When a compatible checkpoint exists, resume restores it and verifies that the next request matches the recorded one byte for byte. Checkpoint restore applies to runs with and without the shell; runs with hooks or per-step models resume by replay and never restore a checkpoint. A checkpoint is not taken while a background job is running. An unfaithful restore is refused and resume falls back to full replay. If saving is disabled, the host warns once with the reason and resume uses full replay. If no checkpoint qualifies, full replay is used; its time grows with the run's length.
- Catch-up re-runs reproducible local tool work and checks, but serves recorded observations for Git, web and jobs. It takes time in proportion to the run's length, though it takes no model time. A checkpoint restore covers the run environment and shell scratch state as of the checkpoint; only the exchanges after it are caught up.
- A rebuilt request that differs from its record may write `resume-divergence.json` and continue live. A tool-tape mismatch, incomplete operation or external operation without `--replay-external` instead refuses resume. On an earlier preview engine we saw request divergence from hash-seed-dependent ordering (fixed in this release) and from journal event-id drift (fixed in later engines).
- Resume needs the same StateFrame version that started the run, and the same model name (or `--model` with the name the server now lists). It refuses a run made by another version, a run that already submitted its result, and a run whose records were changed or damaged.
- Resume keeps the run's original `--max-turns`: passing a different value is refused, except for a run that stopped at its step limit.
- A run that stopped at its step limit resumes only with a larger `--max-turns`, and then restarts live from request 1: the step limit is part of the first request, so neither the checkpoint nor the recorded requests can be reused. `stateframe resume` prints a WARNING when this happens.
- A chat task stopped with Ctrl-C can be resumed with `stateframe resume <its run directory>`; the chat session itself does not pick the result up automatically.
- Checkpoint restore is used only when you resume with the same `--max-turns`, endpoint and model name. Changing the endpoint or `--model` (for a renamed server model) resumes by replay; changing `--max-turns` restarts the run live from request 1 (see above).
- Checkpoint disk use grows with the run and repository. Earlier pre-compression measurements from kill-and-resume runs found state files of 3-21 MB per checkpoint, checkpoint directories of 3-53 MB, and a root of about 175 MB with default retention. On a larger test repository, earlier measurements found 430-460 MB of raw engine state per checkpoint (mostly repository-analysis structures) plus about 0.13 MB per request, about 1.1 GB with two kept, and briefly about 1.7 GB during a save. New `state.pkl` files use zlib level 1 and were about 4x smaller in a measured long replay; the earlier disk totals are historical, not current stored-size promises. Set `STATEFRAME_CHECKPOINT=off` to avoid this disk use; resume then replays the run. When a run finishes for good, StateFrame removes its checkpoints and prints how much it freed; `--keep-checkpoints` (or `STATEFRAME_KEEP_CHECKPOINTS=1`) keeps them. Stopped, cancelled, killed and crashed runs keep theirs. `du` counts copy-on-write file clones, so allocated space can be lower than the displayed total. Before a save, the engine requires free bytes above the greater of 1 GiB and three times the latest saved state's stored size (or a conservative process-memory estimate before the first save). `STATEFRAME_CHECKPOINT_MIN_FREE_BYTES` overrides this floor; `0` disables the check. Low space skips capture and logs one `checkpoint_skipped_low_disk` event per episode, then saving resumes when space recovers. The check does not reserve disk space, and a failed check leaves free space unknown; a write can still fail and be recorded as `checkpoint_failed` while the run continues.
- On Ubuntu 26.04 with Linux kernel 7.0, the kill-and-resume tests can time out before the run reaches the request they interrupt, while the machine is heavily loaded. They pass on macOS, in Linux 6.x containers, and on that host when rerun on their own. This is tracked; it has not been seen to affect a resumed run itself.
- Checkpoints are tied to the engine build and Python version that wrote them. After an upgrade, an old run resumes by replay.
- Loading a checkpoint runs code that was saved with it. Only checkpoints signed with your own install key, owned by you and not writable by others are loaded. Treat a run directory like source code: do not resume one you got from someone else.
- After a checkpoint resume, the time the run spent stopped does not count against an engine time budget; the engine's clock continues from the checkpoint.
- Checkpoint saving needs APFS clones or a POSIX fork; where neither works it saves more slowly or not at all, and resume replays.
